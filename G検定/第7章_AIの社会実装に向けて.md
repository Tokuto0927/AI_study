# G検定 第7章「AIの社会実装に向けて」合格ノート

## 0. この章のゴール

この章のゴールは、AIを「作る技術」ではなく、「ビジネス・社会の中でどう使い、どう運用し、どう成果につなげるか」として理解すること。

G検定では、以下が狙われやすい。

| 領域 | 試験で問われること |
|---|---|
| AIのビジネス利活用 | AIは目的ではなく手段。ROI、経営課題、ビジネス成果と結びつける |
| AIプロジェクトの進め方 | 従来型ウォーターフォールとは異なり、探索的・反復的・継続改善型で進める |
| CRISP-DM / CRISP-ML / MLOps | AI開発はモデル構築だけではない。運用・監視・再学習まで含める |
| データ収集・加工 | AIの精度はデータの量・質・偏り・網羅性に強く依存する |
| アノテーション | 教師あり学習では正解データ作成が重要。ばらつきやルール設計が問われる |
| クラウド / エッジ | それぞれのメリット・デメリットを区別する |
| 学習・評価・推論 | テストデータ、バリデーションデータ、データリーク、再学習が頻出 |

この章は、技術用語の暗記よりも「AIプロジェクトで何に注意すべきか」を選択肢で判断できることが重要。

## 1-2. AI社会実装の基本構造

AI社会実装は、次の流れで考える。

| 順番 | やること | 重要ポイント |
|---|---|---|
| 1 | ビジネス課題を決める | AIを使うこと自体を目的にしない |
| 2 | AI適用の必要性を検討する | ルールベースや通常システムで十分な場合もある |
| 3 | ROI・利益計画を考える | 技術的にできるだけでは不十分 |
| 4 | 業務プロセスを再設計する | AI導入によりBPRが発生する |
| 5 | データを集める | 量・質・偏り・網羅性が重要 |
| 6 | データを加工・アノテーションする | 正解データの品質がモデル精度に影響する |
| 7 | モデルを学習・評価する | バリデーション、テスト、データリークに注意 |
| 8 | 推論環境へデプロイする | クラウド/エッジの選択、軽量化、最適化 |
| 9 | 運用・監視・再学習する | MLOps的に継続改善する |

## 2. 重要用語・概念

## 2-1. AIのビジネス利活用

| 重要語句 | 意味 | 試験での押さえ方 | 間違えやすい点 |
|---|---|---|---|
| AIのビジネス利活用 | AIを使って経営課題を解決し、利益や価値を生み出すこと | 技術的成功とビジネス的成功の両方が必要 | 「AIを導入すれば成功」ではない |
| ROI | 投資対効果。投資に対してどれだけ効果・利益が出るか | AI導入でもROIは重要 | 「革新的AIならROI不要」は誤り |
| ビジネス的成功 | 売上向上、コスト削減、業務改善、顧客価値向上など | 経営方針・成功指標と結びつく | 技術精度だけで判断しない |
| 技術的成功 | モデル精度、処理速度、安定性など技術面で目標を満たすこと | ビジネス成功と両輪 | 技術的成功だけでは不十分 |
| 部分最適 | 一部工程だけを改善すること | 小さな効率化では大きなビジネスインパクトになりにくい | 「5分を1分にする」だけでは弱い |
| 全体最適 | 業務全体・バリューチェーン全体を改善すること | 大きなAI活用では全体最適が重要 | 単独作業の自動化だけで満足しない |

---

## 2-2. AIプロジェクトの進め方

| 重要語句 | 意味 | 試験での押さえ方 | 間違えやすい点 |
|---|---|---|---|
| AIプロジェクト | AIシステムの企画・データ収集・学習・実装・運用・改善まで含む活動 | モデル開発は一部にすぎない | AIモデルを作るだけで完了ではない |
| アジャイル的開発 | 状況に応じて方針を変えながら反復的に進める開発 | AIは最初から全てを想定できないため相性がよい | 従来型ウォーターフォール前提で考えない |
| BPR | Business Process Re-engineering。業務プロセスの再設計 | AI導入時にはBPRが発生することが多い | 現行業務にAIをそのままはめ込むだけでは不十分 |
| フィードバック機構 | 運用で得たデータを蓄積し、AIの再学習・改善に回す仕組み | ビジネス面・技術面の両方で組み込む | 技術上だけの仕組みと考えない |
| PoC | Proof of Concept。概念実証 | 小さく試し、実現可能性や効果を確認する | PoC成功＝本番成功ではない |
| デプロイ | モデルを実際に利用できる環境に配置すること | クラウドやエッジ上に置いて推論可能にする | 学習が終われば自動的に運用できるわけではない |
| サービス化 | AIシステムを継続的に提供・運用する形にすること | AIは納品型よりサービス運用型が望ましい | 「作って納品して終了」はAIに不向き |

---

## 2-3. CRISP-DM / CRISP-ML / MLOps

| 重要語句 | 意味 | 試験での押さえ方 | 間違えやすい点 |
|---|---|---|---|
| CRISP-DM | データマイニングの標準プロセス | 6ステップを押さえる | 最後はRe-learningではなくDeployment |
| Business Understanding | ビジネス理解 | 何を解決するかを明確にする | 技術から始めない |
| Data Understanding | データ理解 | 利用可能なデータを把握する | データがあれば何でも使えるわけではない |
| Data Preparation | データ準備 | 加工・整形・前処理を行う | 生データをそのまま使えるとは限らない |
| Modeling | モデリング | モデルを構築・学習する | ここだけがAIプロジェクトではない |
| Evaluation | 評価 | モデルやビジネス適合性を評価する | 精度だけで評価しない |
| Deployment | 展開・デプロイ | 実運用環境に展開する | Re-learningと間違えやすい |
| CRISP-ML | CRISP-DMを機械学習向けに発展させた考え方 | 監視・保守が追加される | CRISP-DMと完全同一ではない |
| MLOps | Machine Learning + Operations。機械学習を本番運用し続けるための考え方 | 継続的に改善・監視・再学習する | 1回作って終わりではない |

---

## 2-4. クラウドとエッジ

| 重要語句 | 意味 | 試験での押さえ方 | 間違えやすい点 |
|---|---|---|---|
| クラウド | ネットワーク越しの計算資源上でAIモデルを動かす方式 | モデル更新・保守がしやすい | 通信遅延や障害時影響がある |
| エッジ | 利用現場側の端末・機器でAIモデルを動かす方式 | リアルタイム性が高い | モデル更新や機器保守が難しい |
| Web API | ネットワーク越しにシステム間で情報をやり取りする仕組み | 入力データを送り、推論結果を返す形式で使われる | API自体がAIモデルではない |
| オートスケール | 負荷に応じて計算資源を自動調整する仕組み | クラウド提供時に重要 | エッジでは通常1機器1モデルのように負荷が固定的 |

---

## 2-5. データ収集・加工・学習

| 重要語句 | 意味 | 試験での押さえ方 | 間違えやすい点 |
|---|---|---|---|
| オープンデータセット | 公開されているデータセット | 利用条件・ライセンス確認が必要 | 商用利用できるとは限らない |
| データの質 | 画像の鮮明さ、音声の品質、必要情報の有無など | 質が悪いと学習できない | データ量だけでは不十分 |
| データの偏り | 訓練データが現実の分布を反映していない状態 | バイアスや精度低下の原因 | 多数派クラスばかり学習しやすい |
| データの網羅性 | 想定される状況を広く含んでいること | 未学習の状況では推論が難しい | 少量データで万能にはならない |
| 前処理 | 生データを学習しやすい形に加工すること | 動画→静止画、文字→数値・ベクトルなど | 生データをそのまま使えると思わない |
| アノテーション | 教師あり学習用の正解ラベルを付ける作業 | ばらつき防止のためルール・レビューが必要 | 人が付ければ必ず正しいわけではない |
| 匿名加工 | 個人を特定できないようデータを加工すること | 法的・プライバシー・セキュリティリスク対策 | 個人情報をそのまま学習に使わない |
| 転移学習 | 既存の学習済みモデルを別タスクに活用する手法 | 少量データでも学習を安定させやすい | 元タスクと新タスクの関連性が重要 |
| バリデーションデータ | モデル調整に使う検証用データ | テストデータとは分ける | テストデータを見ながら調整しない |
| テストデータ | 最終的な性能評価に使うデータ | 未知データへの性能確認に使う | 学習や調整に使うと評価が歪む |
| データリーク | 本来知るべきでない情報が学習に混入すること | 評価が不当に高くなり、本番で失敗する | 高精度に見えても実力ではない |
| 推論 | 学習済みモデルで予測・分類を行うこと | 学習時と運用時の環境差に注意 | 学習と推論は同じではない |

## 3. 重要論点の整理

## 3-1. AIは目的ではなく手段

AIプロジェクトで最初に考えるべきことは、「AIをどう使うか」ではなく「何を解決したいか」。

| 正しい考え方 | 誤った考え方 |
|---|---|
| 経営課題・業務課題を解決するためにAIを使う | AIを導入すること自体を目的にする |
| ROIや利益計画を考える | 革新的AIならROIは不要と考える |
| 技術的成功とビジネス的成功を両方見る | モデル精度だけを見る |
| 中長期でデータ蓄積と改善を見る | 初期精度だけで判断する |

試験では「AIは技術的要素が大きいので経営方針と分離して考えるべき」のような選択肢は誤り。

---

## 3-2. AIプロジェクトは従来型システム開発と違う

| 観点 | 従来のシステム開発 | AIプロジェクト |
|---|---|---|
| 前提 | 人が仕様を決め、人の想定通りに動かす | データから学習し、初期から全てを想定できない |
| 進め方 | ウォーターフォール型が多い | アジャイル的・反復的 |
| 成果物 | プログラム・システム | モデル、データ、運用基盤、改善サイクル |
| 運用 | 納品後は保守中心 | データ収集・再学習・改善が重要 |
| リスク | 仕様漏れ・バグ | 精度不足、データ偏り、環境変化、説明責任 |

AIプロジェクトは「モデルを作るフェーズ」だけでは成立しない。
企画、データ、業務設計、運用、評価、改善が重要。

---

## 3-3. AI適用時にはBPRが必要になりやすい

BPRとは、業務プロセスそのものを再設計すること。

例：工場の外観検査をAI化する場合

| 悪い考え方 | 問題 |
|---|---|
| 人がやっていた検査部分だけAIに置き換える | 検査後に製品を運ぶ作業が残り、人件費削減にならない可能性 |
| 現行業務にAIをそのまま差し込む | 業務全体のコストが下がらない可能性 |
| AI導入後のコストを見ない | ROIが悪化する可能性 |

正しい考え方は、「検品」「移動」「確認」「例外対応」などを分解し、業務全体を再設計すること。

---

## 3-4. フィードバック機構が重要

AIは運用しながら改善する。

| 項目 | 内容 |
|---|---|
| データ蓄積 | 運用中に新しいデータを集める |
| フィードバック | ユーザーや業務結果から正解・修正情報を得る |
| 再学習 | 蓄積データでモデルを更新する |
| 精度向上 | 推論精度や安定性を高める |
| コスト改善 | より少ないコストで大きな成果を出す |

試験では「技術上にだけフィードバック機構を組み込む」が誤りになりやすい。
正しくは「ビジネス上も技術上も」組み込む。

---

## 3-5. クラウドとエッジの違い

| 観点 | クラウド | エッジ |
|---|---|---|
| 処理場所 | クラウド上のサーバ | 利用現場の端末・機器 |
| モデル更新 | 一元管理しやすく更新が楽 | 現場機器ごとの更新が必要で難しい |
| 保守 | 計算機の保守運用が比較的楽 | 機器を長期保守する必要がある |
| 通信 | ネットワーク遅延の影響を受ける | 通信量が少なくリアルタイム性が高い |
| 障害時影響 | クラウド障害時の影響が大きい | 機器単位で影響範囲が小さい |
| コスト | 利用量・推論回数・サーバ数に応じて変動 | デバイス選定・保守コストが重要 |
| 代表例 | Web APIで推論 | 工場カメラ、車載、スマートデバイス |

引っかけ：
- 「エッジは装置が手元にあるからモデル更新が容易」→誤り
- 「エッジではモデル更新が不要」→誤り
- 「クラウドは通信遅延を考慮する必要がある」→正しい
- 「エッジは故障影響範囲が小さい」→正しい

---

## 3-6. AIプロジェクト体制

AIプロジェクトには、多様な役割が必要。

| 役割 | 主な役割 |
|---|---|
| マネージャー | ビジネス目標、ROI、システム構成、意思決定 |
| データサイエンティスト | データ分析、モデル構築、学習・評価 |
| AIエンジニア / システムエンジニア | AIモデルを組み込むシステム、API、基盤、運用環境の構築 |
| UI/UXデザイナー | 人がAI結果を確認・修正・フィードバックできる画面や業務導線を設計 |
| 業務担当者 | 現場知識、正解データ、例外ケースの提供 |
| 法務・セキュリティ担当 | 個人情報、契約、利用条件、リスク管理 |
| ユーザー / ステークホルダー | 利用者視点、想定外の影響確認 |

試験では「AIモデルを構築する役割だけでよい」は誤り。

---

## 3-7. CRISP-DMの6ステップ

| 順番 | ステップ | 内容 |
|---|---|---|
| 1 | Business Understanding | ビジネスの理解 |
| 2 | Data Understanding | データの理解 |
| 3 | Data Preparation | データの準備 |
| 4 | Modeling | モデリング |
| 5 | Evaluation | 評価 |
| 6 | Deployment | 展開・デプロイ |

重要：
- CRISP-DMは完全な一直線ではなく、行ったり来たりする。
- 最後はDeployment。
- Re-learningではない。

---

## 3-8. CRISP-ML

CRISP-MLは、CRISP-DMを機械学習向けに発展させた考え方。

| 項目 | CRISP-DM | CRISP-ML |
|---|---|---|
| 主な対象 | データマイニング | 機械学習 |
| 特徴 | ビジネス理解、データ理解、準備、モデリング、評価、展開 | 監視・保守を重視 |
| 試験ポイント | Deploymentを含む | Monitoring and Maintenanceが追加される |

---

## 3-9. MLOps

MLOpsは、Machine LearningとOperationsを組み合わせた考え方。
DevOpsから派生した概念。

| 項目 | 内容 |
|---|---|
| 目的 | AIモデルを本番環境で継続的に運用・改善する |
| 対象 | データ収集、検証、特徴量抽出、学習、推論基盤、監視、再学習など |
| 重要点 | AIモデル構築は全体の一部にすぎない |
| 試験ポイント | 全プロセスを1回やって終わりではなく、運用中も継続して回す |

MLOpsで狙われる誤答：
- 「モデル構築がAIプロジェクトの中心であり、周辺は小さい」→誤り
- 「本番投入後は基本的にプロセスを回さない」→誤り
- 「運用時も継続して改善する」→正しい

---

## 3-10. データ収集のポイント

| データ収集方法 | 内容 | 注意点 |
|---|---|---|
| オープンデータセット | 公開データを利用する | ライセンス・商用利用可否を確認 |
| 自分で収集 | センサ、カメラ、マイク、ログ、アンケートなどで集める | コスト・ROI・収集方法を検討 |
| 外部購入 | 外部からデータを買う | 利用条件・品質・権利確認が必要 |

代表的なオープンデータセット例：

| 分野 | 例 |
|---|---|
| 画像・コンピュータビジョン | ImageNet、Pascal VOC、MS COCO |
| 自然言語処理 | WordNet、SQuAD、DBpedia |
| 音声 | LibriSpeech |

---

## 3-11. 学習可能なデータの条件

| 条件 | 意味 | 不十分だとどうなるか |
|---|---|---|
| 必要情報が含まれる | 認識対象が十分に写っている・記録されている | モデルが学習できない |
| データの質が良い | 画像が鮮明、音声が明瞭など | 精度が下がる |
| 偏りが少ない | 現実の分布を反映している | 特定クラスに偏った予測になる |
| データ量が十分 | 学習に必要な数がある | 汎化性能が低くなる |
| 網羅性がある | 想定される状況を広く含む | 未経験の状況で推論できない |

章末問題では、
「データのラベルが偏っている」
「データ数が少ない」
「データの質が悪い」
は学習できない原因として正しい。

「データの数が多すぎる」は基本的には原因として不適切。

---

## 3-12. データの偏りとバイアス

分類問題では、データ数が多いクラスを優先して学習しやすい。

| 例 | 問題 |
|---|---|
| 正常品画像が大量、不良品画像が少量 | 正常品ばかり高精度で、不良品検出が弱い |
| 晴天時の画像ばかり | 雨天・夜間で精度低下 |
| 若年層データばかり | 高齢者に対する予測精度が低下 |
| 標準的なケースばかり | レアケースに弱い |

試験では「データが多ければ偏りは問題にならない」という選択肢に注意。
データが多くても偏っていれば問題になる。

## 3-13. 前処理・アノテーション

## 前処理の例

| データ | 前処理の例 |
|---|---|
| 動画 | 静止画に切り出す |
| 画像 | 対象領域を切り抜く、サイズを揃える |
| テキスト | 文字・単語を数値やベクトルに変換する |
| DBデータ | 複数テーブルから集約する |
| 音声 | ノイズ除去、特徴量化する |

## アノテーションの注意点

教師あり学習では、正解データを作成する必要がある。
この正解付け作業がアノテーション。

| 問題 | 内容 |
|---|---|
| 定義の曖昧さ | 何を正解とするか判断軸が曖昧 |
| 作業者の感性差 | 人によってラベル判断が変わる |
| 専門性不足 | 専門知識がないと正しく付けられない |
| 作業量過多 | 大量データで集中力が落ちる |
| ケアレスミス | 単純な付け間違い |

対策：

| 対策 | 内容 |
|---|---|
| マニュアル作成 | 判断軸・サンプル・作業精度を明確にする |
| レビュー | 複数人作業のばらつきを検出する |
| 作業者アサイン | 専門性や作業適性に応じて割り当てる |
| ルール改善 | 作業中の曖昧点を反映してマニュアルを更新する |

## 3-14. 個人情報と匿名加工

AI開発では、アンケート、顔画像、音声、ログなどに個人情報が含まれることがある。

| 対応 | 内容 |
|---|---|
| 削除 | 氏名・住所など個人識別情報を消す |
| マスキング | 個人を特定できる部分を隠す |
| 集約化 | 個人単位ではなく統計情報にする |
| 特徴量化 | 生データを復元しにくい特徴量に変換する |
| 生データ削除 | 画像・音声などの元データを保持しない |

試験では「個人情報を含むデータをそのまま保持・利用してよい」は危険。

## 3-17. モデル学習・評価

| 論点 | 内容 | 試験での押さえ方 |
|---|---|---|
| パラメータ調整 | モデル精度や学習安定性に影響 | 不適切だと過学習・不安定化 |
| 精度向上の限界 | ある程度精度が出ると数%改善にも大きなコストがかかる | ビジネス目標との折り合いが重要 |
| 転移学習 | 学習済みモデルを別タスクに使う | 少量データでも安定しやすい |
| バリデーションデータ | モデル調整用 | テストデータとは分ける |
| テストデータ | 最終評価用 | 調整に使うと評価が歪む |
| データリーク | 本来知らない情報が学習に混入 | 評価が不当に高くなり、本番で失敗する |

## 3-18. 推論と運用

| 項目 | 内容 |
|---|---|
| 推論 | 学習済みモデルで実データに対して予測・分類を行うこと |
| 学習時 | GPUなど高性能計算資源を使うことが多い |
| 推論時 | CPUやエッジデバイスを使うことも多い |
| モデル軽量化 | 推論環境に合わせてモデルを小さく・速くする |
| 再学習 | 環境変化やデータ変化に対応するために行う |
| 精度低下 | 入力データや撮影対象の変化、センサ劣化などで起きる |

章末問題では、
「モデルや計算機は時間経過で通常劣化して違う結果を返す」
という考えは基本的に誤り。
カメラなど計測デバイスの劣化、撮影対象や環境の変化が原因として狙われる。

## 4. 似た用語の違い

## 4-1. 技術的成功とビジネス的成功

| 用語 | 意味 | 例 |
|---|---|---|
| 技術的成功 | AIモデルやシステムが技術的に期待性能を出すこと | 精度90%、処理速度1秒以内 |
| ビジネス的成功 | 経営・業務上の成果が出ること | コスト30%削減、売上向上、作業時間短縮 |

引っかけ：
「ビジネスでAIを使うとき最も重要なのは技術的成功である」
→誤り。ビジネス的成功と技術的成功は両輪。

---

## 4-2. PoCと本番運用

| 用語 | 意味 | 注意点 |
|---|---|---|
| PoC | 小さく試して実現可能性を確認する | PoC成功だけでは本番成功とは言えない |
| 本番運用 | 実際のユーザー・業務で継続利用する | 監視、再学習、障害対応、コスト管理が必要 |

---

## 4-3. CRISP-DMとMLOps

| 観点 | CRISP-DM | MLOps |
|---|---|---|
| 位置づけ | データ分析・データマイニングの標準プロセス | 機械学習の本番運用・継続改善の考え方 |
| 主眼 | 分析プロセス | 運用・監視・再学習 |
| 重要語 | Deployment | Continuous operation / Monitoring / Maintenance |
| 試験の注意 | Re-learningではなくDeployment | 1回で終わらず継続して回す |

---

## 4-4. クラウドとエッジ

| 観点 | クラウド | エッジ |
|---|---|---|
| 更新 | しやすい | 難しい |
| 遅延 | 通信遅延あり | リアルタイム性が高い |
| 通信量 | 多くなりやすい | 少ない |
| 障害範囲 | 大きい可能性 | 機器単位で小さい |
| 保守対象 | クラウド環境 | 現場デバイス |
| 代表的注意点 | オートスケール、通信、コスト | デバイススペック、モデル更新、長期保守 |

---

## 4-5. バリデーションデータとテストデータ

| 用語 | 使うタイミング | 目的 |
|---|---|---|
| 学習データ | 学習時 | モデルを学習させる |
| バリデーションデータ | 調整時 | ハイパーパラメータやモデル選択に使う |
| テストデータ | 最終評価時 | 未知データへの性能を評価する |

引っかけ：
テストデータの結果を見ながらモデル調整を繰り返すと、テストデータに過度に適合し、正しい評価ができなくなる。

---

## 4-6. データ不足・データ偏り・データリーク

| 用語 | 意味 | 起こる問題 |
|---|---|---|
| データ不足 | 学習に必要な量が足りない | 精度が低い、汎化しない |
| データ偏り | データ分布が現実とずれている | 一部クラスに弱い、バイアスが出る |
| データリーク | 本来使えない情報が学習に混ざる | 評価だけ高く、本番で精度低下 |

| エッジの強みは？ | リアルタイム性、通信量の少なさ、障害影響範囲の小ささ |
| アノテーションで大事なことは？ | 判断軸、マニュアル、レビュー |
| データリークの問題は？ | 評価が高く見え、本番で性能が出ない |
| 精度低下時に確認すべきものは？ | 入力データ、センサ、対象環境の変化 |

## 10. 最短復習用まとめ

## 10-1. 30秒まとめ

第7章は「AIを社会・ビジネスで使うにはどうするか」の章。

AIは目的ではなく手段。
技術的に精度が出ても、ROIや業務プロセス、運用体制が悪ければ失敗する。
AIプロジェクトはモデル開発だけでなく、データ収集、加工、学習、評価、デプロイ、運用、監視、再学習まで含む。
CRISP-DMの最後はDeployment。
MLOpsは本番運用後も継続改善する考え方。
クラウドは更新しやすいが通信遅延や障害影響がある。
エッジはリアルタイム性が高いが更新・保守が難しい。
データは量・質・偏り・網羅性が重要。
データリークは評価を不当に高くし、本番で失敗する。

## 10-3. これだけは落とさない

1. AIは目的ではなく、ビジネス課題解決の手段。
2. AI導入でもROIは必須。
3. 技術的成功とビジネス的成功は両輪。
4. AIプロジェクトはモデル開発だけではない。
5. AI導入時はBPRが必要になりやすい。
6. フィードバック機構はビジネス上・技術上の両方に必要。
7. CRISP-DMの最後はDeployment。
8. MLOpsは継続運用・監視・再学習の考え方。
